Why This Project

为什么需要把 VLA 资料做成数据库

VLA 模型相关信息散落在论文、项目主页、GitHub 仓库、Hugging Face 模型卡和 benchmark 表格中。 只靠 Excel 或人工笔记会让多对多关系、条件查询、来源追溯和统计分析变得越来越难维护。

字段口径不统一

模型年份、论文状态、topic、benchmark split 和开源状态在不同来源里经常命名不同。

关系天然复杂

一篇论文有多个作者，一个作者可能有多个机构，一个模型也可能对应多个 topic 和数据来源。

多条件查询困难

按年份、范式、topic、benchmark 或关键词组合筛选，需要稳定的关系模式和联查逻辑。

统计与扩展成本高

新增 2026 模型、benchmark 或评测结果时，规范化结构能减少重复、空缺和不一致。

Data Scope

模型记录和论文索引分开管理

系统维护一组人工核对的核心模型记录，并从论文索引中为明确提出模型或模型级方法的论文生成轻量模型记录； 论文索引侧重 VLA 模型、机器人基础模型、语言条件策略、action tokenization 以及模型适配/加速方法，不再把纯数据集或 benchmark 当作主记录。 每条 2026 模型和论文记录都尽量附上论文页、项目页或代码链接。

Design Architecture

三层实现结构

先明确关系模式，再组织查询逻辑，最后通过服务端渲染页面展示数据库能力。

Layer 1

Data Layer: MySQL Schema

核心实体、参考表、中间表和事实表分离，保证结构规范化与关系清晰。

  • Model / Paper
  • Author / Affiliation
  • Topic / PaperTopic
  • Benchmark / EvaluationResult
Layer 2

Service Layer: Flask + SQLAlchemy

通过 ORM 维护外键关系，用路由组织列表页、详情页、统计页、timeline 和管理录入逻辑。

  • joined query
  • filtering
  • aggregation
  • paper search
Layer 3

Web Layer: Flask Pages

页面展示查询结果、统计分布、E-R 设计和管理操作，不把数据库逻辑塞进静态前端。

  • Models / Papers
  • Benchmarks / Stats
  • SQL / Schema
  • Admin Forms

ER Design

核心 E-R 图与关系模式

本项目采用规范化设计，不把全部信息塞进一张大表。多值属性通过桥接表表达， benchmark 结果单独拆成事实表，便于后续扩展更多评测记录。

核心实体

models、papers、authors、 affiliations、benchmarks 是主要业务对象。

桥接表

paper_authors、author_affiliations、 model_topics、paper_topics、model_data_sources 用于表达多对多关系。

参考表

paradigms、topics、 data_source_types 统一分类口径，保证筛选和统计可靠。

事实表

evaluation_results 单独保存 metric、split、来源链接与备注， 支撑一个模型对应多个 benchmark 结果。

Relationship Summary

主要实体关系

Paradigm → Model 一对多。一个范式可对应多个模型。
Paper → Model 一对多。一个论文记录可关联一个或多个模型。
Paper ↔ Author 多对多。通过 paper_authors 保存作者顺序、第一作者和通讯作者标记。
Paper ↔ Topic 多对多。通过 paper_topics 给论文索引复用统一 topic 分类。
Author ↔ Affiliation 多对多。通过 author_affiliations 关联机构。
Model ↔ Topic 多对多。通过 model_topics 支持一个模型对应多个研究主题。
Model ↔ DataSourceType 多对多。通过 model_data_sources 表达 real robot、simulation、synthetic 或 mixed。
Model → EvaluationResult ← Benchmark 两个一对多共同构成评测结果事实表，支撑 benchmark 维度联查和统计。

Curation Rules

数据原则：来源清楚，空缺留空

数据库覆盖 2024-2026 的近期模型，并用论文索引补足上下文。 没有公开来源支撑的信息不会手动补猜。

01

未知字段保留为空

没有公开来源支撑的字段不靠猜测补齐，数据库中保留空值或 NULL。

02

数值结果必须有来源

只有官方页面、论文或模型卡明确给出数值时，才写入 metric_value 与单位。

03

允许定性结果记录

如果公开页面只有文字描述，则只写 result_summary 和 source_url。

04

分类口径集中维护

topic、paradigm、data source 和 benchmark 使用参考表，避免自由文本导致统计失真。
